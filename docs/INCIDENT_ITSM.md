# Инциденты и МосИТСМ

Инциденты хранятся отдельно от задач и миноров. Миграция
`20261029_incident_itsm.sql` добавляет локальный комментарий и поля архива;
существующие записи остаются активными. Данные не удаляются.

## Подключение

В существующем серверном окружении API задаётся `MOS_ITSM_TOKEN=<token>`.
Токен не передаётся в браузер, документацию или репозиторий. Используется
только `https://api.itsm.mos.ru/v1`, Bearer и `X-4me-Account: echd`.
Client ID не требуется. Все обращения к МосИТСМ — GET.

`GET /incidents/:id/itsm` требует пользовательскую сессию и каждый раз
загружает карточку, комментарии/заметки, audit, метаданные вложений и
доступные связанные коллекции. Загружаются все страницы в пределах
100 страниц на раздел, 250 запросов, 32 МиБ и 60 секунд на просмотр.
Недоступный или частично полученный раздел помечается отдельно.
Отказ в доступе не означает отсутствие записей. Файлы вложений автоматически
не скачиваются. HTML в заметках очищается; внешние изображения представлены
ссылками и сами не загружаются.

## Синхронизация

`POST /incidents/:id/itsm/sync` принимает только текущую `version`, заново
читает карточку и атомарно заменяет четыре поля: важность → приоритет
(`top` → `high`), `resolution_target_at` → исходная дата сгорания,
`status=waiting_for` → отложен, `waiting_until` → отложен до.
Jira-ссылка, номер и локальный комментарий сохраняются.
Неизвестные важность/даты или противоречивое ожидание блокируют всю запись.
Конкурентная правка возвращает 409. В архиве синхронизация отключена.

## Архив

Локальные состояния: `active`, `completed` (выполнен в срок), `burned`
(срок нарушен). Они не подменяют текущий статус МосИТСМ.
Ручное закрытие через `POST /incidents/:id/close` записывает результат,
источник `manual` и срок, действовавший при закрытии. Автоматика больше
не обращается за этой записью и не меняет её результат.

Если токен настроен, сервер раз в минуту выбирает активные записи, у которых
до действующего срока осталось не больше пяти минут. Проверка работает
без открытой страницы. Продлённый срок из МосИТСМ запоминается отдельно;
до приближения нового срока повторного опроса нет. Проверка не выполняет
массовую синхронизацию пользовательских полей.

При `completed` сравнивается `completed_at` с действующим сроком:
завершение не позже срока — успешно, позже — сгорел. Незавершённый инцидент
после срока также сгорел. Наблюдавшаяся отсрочка сохраняется для сравнения,
если МосИТСМ очищает ожидание при завершении; при отсутствии такого снимка
используется сохранённая локальная отсрочка. Достоверность неизвестной ранее
отсрочки после её удаления из источника автоматически не восстанавливается.
Отсутствующая дата завершения, ожидание без даты или ошибка API оставляют
запись активной с ошибкой и повторной попыткой через пять минут.

Результат и срок сравнения сохраняются в `closure_source`, `closed_at`,
`closure_deadline_at`, `itsm_completed_at`; версия защищает ручную правку
от одновременно выполняющегося автоматического запроса.

## Выпуск

Перед миграцией нужна свежая копия PostgreSQL с проверкой восстановления
в отдельную временную БД, включая количество инцидентов и документов.
Сначала выпускается backend с миграцией и серверным токеном, затем frontend.
Проверяются health, новые маршруты, исходные количества рабочих сущностей
и чтение реального инцидента. Изменение/закрытие рабочих инцидентов для QA
не выполняется; эти сценарии проверяются на тестовой БД и локальном стенде.

## Исходящий worker ноутбука

Автор: Иванов А.

При `MOS_ITSM_TRANSPORT=relay` единый клиент МосИТСМ использует очередь
в памяти процесса API. Этот транспорт применяется к подробностям,
синхронизации и серверной проверке сроков. Прямого fallback с production нет.
Отдельный случайный `MOS_ITSM_RELAY_TOKEN` (не менее 32 символов) разрешает
только получение заданий и отправку результатов. Пользовательские сессии
и интеграционные ключи задач не заменяют этот ключ.

Worker сам устанавливает HTTPS-соединение с `api.simpletracker.ru`:

- `GET /integrations/itsm-relay/jobs?capacity=4`: long polling до 20 секунд;
- `POST /integrations/itsm-relay/jobs/:id/result`: ответ конкретного задания;
- `GET /integrations/itsm-relay/status`: состояние канала без содержимого.

Авторизация: заголовок `X-ITSM-Relay-Token`. В заданиях нет токена МосИТСМ.
Worker читает только `https://api.itsm.mos.ru/v1/requests/<number>` и
разделы, перечисленные в клиенте. Допустимы только параметры `page`
и `per_page` (до 100). Произвольные адреса, другие методы, редиректы,
встроенные пароли и отключение TLS не поддерживаются.

Не более четырёх одновременных чтений на worker, 64 ожидающих запросов
на API. Задание живёт 11 секунд; у каждого случайные ID и nonce.
Неверный nonce, повтор, отменённое и просроченное задание возвращают 409.
Один ответ ограничен 12 МиБ; общий клиент сохраняет пределы 32 МиБ,
250 запросов и 60 секунд. Передаются исходные байты JSON, HTTP-статус и
Link; ошибка отдельного раздела не скрывает остальные. Очередь не содержит
постоянного кэша: открытие подробностей создаёт новые запросы.

При остановке ноутбука пользователь получает 503 (или 504 у уже выданного
задания); записи не синхронизируются и не архивируются по ошибке связи.
Перезапуск API сбрасывает очередь: текущий просмотр может потребовать
повтора. Worker переподключается сам с паузой до 15 секунд.

### Установка и хранение credentials

`worker/requirements.txt`, `worker/worker.py` и
`worker/simpletracker-itsm-worker.service` содержат воспроизводимые
исходники. Установка выполняется в
`~/.local/share/simpletracker-itsm-worker/` с отдельным Python venv.
`worker/enroll.py` читает объект с `itsm_token` и `relay_token` из
защищённого stdin (не из аргументов и не из файла с открытыми токенами).

Долговременное хранилище: AES-256-GCM `credentials.vault` (0600), отдельный
бинарный ключ `~/.config/simpletracker-itsm-worker/vault.key` (0600), оба
каталога 0700. Systemd передаёт ключ в runtime через `LoadCredential`;
расшифрованные токены существуют только в памяти worker. Это программное
шифрование с файловыми правами, не TPM и не защита от владельца учётной
записи/root. Не копировать ключ и vault в Git или общие резервные архивы.

Сервис пользовательский, `loginctl ... Linger=yes` обеспечивает запуск
после загрузки ОС. Сервис работает с `Restart=always`, ограниченными
правами и файловой системой только для чтения. Ноутбук должен оставаться
включённым, не спящим и иметь доступ к сети; VPN и настройки сна не меняются.

### Эксплуатация

Команды выполняются от пользователя, установившего worker:

```bash
systemctl --user start simpletracker-itsm-worker
systemctl --user stop simpletracker-itsm-worker
systemctl --user restart simpletracker-itsm-worker
systemctl --user status simpletracker-itsm-worker --no-pager
journalctl --user -u simpletracker-itsm-worker -n 50 --no-pager
```

Для автоматического старта: `systemctl --user enable simpletracker-itsm-worker`;
для его отмены: `systemctl --user disable --now simpletracker-itsm-worker`.
В журнале только состояние канала, безопасные классы ошибок и HTTP-коды;
номера инцидентов, переписка и credentials не записываются.

Изменения схемы БД для relay не требуются. Проверки записи выполняются
на PGlite с отдельными тестовыми данными; production-проверка — только GET.
