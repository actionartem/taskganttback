## Проверенный состав

Добавочная миграция `migrations/20261026_tracker_v2.sql`:

- `users.session_generation` для отзыва сессий;
- пять полей задачи: подтверждённый срок, следующее действие/его срок, ожидаемый ответ/его срок;
- `task_events`, `task_jira`, `task_documents`, `tracker_preferences`, `attention_snoozes`;
- `task_change_log.event_id` связывает новый журнал с прежним без повторов.

Существующие задачи, пользователи, почтовые тексты, история и экспорт не удаляются. Файлы документов хранятся в PostgreSQL (BYTEA, максимум 10 МиБ), в существующем постоянном volume `tasktracker_pgdata`. Резервная копия БД включает файлы. Большой архив документов потребует отдельного решения, не входящего в этот выпуск.

## Порядок установки после подтверждения

1. Перепроверить текущие Git SHA, статус контейнеров, свободное место и отсутствие чужих правок; зафиксировать прежний frontend symlink и backend image ID. Изменившийся сервер требует повторной сверки.
2. На сервере сохранить закрытую копию текущих `.env` и nginx-конфига для отката. Значения не выводить и не переносить на локальный компьютер.
3. Передать и выполнить `scripts/verify-v2-backup.sh`. Скрипт создаёт дамп, восстанавливает его в отдельную временную БД, сверяет количества строк основных таблиц, сохраняет checksum и удаляет только свою временную БД. Production-схему не меняет. Ошибка любого шага останавливает выпуск; `.partial` не считается готовой копией. Не переделывать регулярный backup-сервис.
4. Только после проверки копии добавить в production `.env` независимые случайные `SESSION_SECRET` (не менее 32 символов), `AGENT_API_TOKEN`, `JIRA_INGEST_TOKEN`; установить `TELEGRAM_NOTIFICATIONS_ENABLED=false`. Существующие почтовые ключи и правила сохранить. Compose уже читает `.env` для API. Новые ключи не печатать, не коммитить, не отправлять агенту без указания владельца о защищённом способе передачи.
5. В API server-блоке файла `/etc/nginx/sites-available/migrated-apps.conf`, внутри уже существующего `location /`, добавить `client_max_body_size 16m;`. Это нужно для JSON с base64 файла до 10 МиБ; Express отдельно ограничивает обычные запросы. Сохранить текущие CORS/proxy-заголовки, сертификаты и listen. Соседний точный `location = /razdelit/contact` с лимитом 8k не изменять. Выполнить `nginx -t`, затем reload только при успехе.
6. Выпустить backend раньше frontend. Существующий workflow применяет ещё не зарегистрированные миграции с `ON_ERROR_STOP=1`, затем пересоздаёт API. Новая миграция проверена на повторный запуск. Не обходить проверку копии из шага 3 только потому, что workflow тоже вызывает pg_dump.
7. Убедиться, что API запущен с новой схемой и секретами; проверить `/health`, `/openapi.json` (version 2.0.0), `/integrations/guide`, авторизованное чтение задач и прежние 77 задач с учётом легитимных изменений за время работы.
8. Выпустить frontend с `NEXT_PUBLIC_API_BASE=https://api.simpletracker.ru`. Проверить GitHub Actions, новый release symlink, файлы `out`, домен с `?v=<sha>` и вход. После нового ключа и формата токенов потребуется повторный вход; пароли пользователей не меняются.
9. Согласованный тест записи: отдельная явно тестовая задача, изменение + тег + история, файл без рабочих данных, чтение и повтор того же внешнего события. Сверить результат через GET и UI. Не отправлять рабочие уведомления. Удаление контрольных данных — только как часть подтверждённого сценария.
10. Проверить оба agent-ключа: разрешённые операции работают, чужая область возвращает 401. Реальный сборщик Jira и первичные рабочие документы настраивает внешний агент по инструкции; один успешный тест API не доказывает, что этот сборщик уже работает.
11. Подтвердить `inactive` и `disabled` у Telegram-бота, отсутствие отправки из API. Зафиксировать версии и результаты, затем обновить корневой AGENTS.md по фактически установленной системе.

## Откат

При ошибке до миграции остановить выпуск, сохранив прежний backend/frontend. При ошибке после добавочной миграции вернуть прежний backend image и frontend release; новые таблицы/колонки оставить, не выполнять DROP и не восстанавливать дамп поверх работающей БД автоматически. Данные, поступившие после снимка, иначе потеряются. Восстановление БД — отдельное решение владельца.

Старый backend после отката не поддерживает новые agent-маршруты и простой отзыв сессий, может снова включить старую отправку Telegram. Поэтому откат API требует отдельной проверки уведомлений; остановленный бот не защищает от прямой отправки самим API. В случае ошибки нового backend безопаснее временно остановить только API, чем автоматически включать непроверенный старый режим. Нельзя считать один HTTP 200 подтверждением успешного отката.

- Бот: синтаксическая проверка; `/debugnotify` удалён в локальном исходнике. Не развёртывать его через workflow, пока бот должен быть выключен.
